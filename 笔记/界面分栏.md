前言

Crossdating_Tauri 的首页不是一个纯展示页面，它同时承载了三类重量级内容：

- 左侧树轮宽度数据编辑区
- 左下潜在问题详情区
- 右侧 COFECHA 文本与图表区

在项目早期，这几个区域虽然能工作，但整体布局更像是“静态堆叠的结果”，而不是一套真正可调整、可持久化、可在窄窗口下优雅退化的分栏系统。

后来首页逐步演进出三个明确需求：

1. 左右两大栏可以拖动调整宽度。
2. 左侧上下两块和右侧上下两块也都可以继续拖动调整。
3. 当空间不足时，不应该简单卡死在某个尺寸，而应该让内容在合适的容器内滚动。

这篇笔记记录的不是“加了几个 splitter”，而是当前项目里这套分栏系统是怎么落地的，以及它为什么最终长成现在这个样子。

正文

问题从哪里开始

最初的需求其实很直接：给首页加可拖拽分栏。

但真正开始做之后，很快就发现这不是单纯的“插一条分隔线”就能结束的事情。因为首页同时牵涉：

- flex 布局
- 多层滚动容器
- 文本区和图表区的高度竞争
- 左侧大数据表格的渲染成本
- 用户关闭应用后仍然希望保留上次布局

所以最后这套分栏实践，实际上解决的是四件事：

1. 明确首页到底有哪几组可调整边界。
2. 统一拖拽状态和持久化逻辑。
3. 把最小尺寸的责任放到正确的层级。
4. 让布局在窗口缩小时优先转为滚动，而不是硬拦截拖拽。

首页最终被抽象成哪三组分栏

当前首页最终稳定下来的，是三组分栏：

1. 主分栏
   `width-module | cofecha-module`

2. 左侧上下分栏
   `data-container | problems-container`

3. 右侧上下分栏
   `full-text | line-chart`

对应代码都接在 [Home.tsx](</d:/Code/Crossdating_Tauri/src/pages/Home.tsx>) 里，而拖拽逻辑统一交给 [useResizablePanels.ts](</d:/Code/Crossdating_Tauri/src/pages/useResizablePanels.ts>)。

为什么单独抽一个 `useResizablePanels`

如果把所有拖拽细节都塞在 `Home.tsx`，很快就会把页面入口搞成一团：

- 哪个分隔条对应哪个比例
- 当前是横向拖还是纵向拖
- 事件绑定与解绑
- 最小尺寸换算
- 本地持久化
- 拖拽中的视觉状态

所以最终把这些横切关注点抽成了一个专用 hook。

当前这个 hook 维护三份布局比例：

```ts
const DEFAULT_LAYOUT = {
    mainSplitRatio: 0.5,
    leftBottomRatio: 0.12,
    rightBottomRatio: 0.35,
} as const;
```

并把它们持久化到：

```ts
localStorage["crossdating.homeLayout.v1"]
```

这样首页在重新打开后，可以恢复上一次的相对布局。

为什么存“比例”而不是“像素”

因为这是一个桌面窗口应用，用户会频繁改窗口尺寸。

如果直接存像素值，就会出现两个问题：

1. 同样的布局在不同窗口大小下会失真。
2. 恢复布局时容易出现某边过宽或过窄。

存比例的好处是：

- 窗口变化时，分栏会自然随容器缩放；
- 重启应用后恢复的是“相对布局感”；
- 分栏状态更稳定，不依赖某个绝对分辨率。

拖拽逻辑是怎么实现的

当前实现采用的是最直接的一套 `pointerdown -> pointermove -> pointerup` 机制。

核心配置长这样：

```ts
type ResizeConfig = {
    key: LayoutKey;
    axis: "x" | "y";
    container: HTMLElement | null | (() => HTMLElement | null);
    minStart: number;
    minEnd: number;
};
```

几个关键点值得单独记一下。

第一，`container` 支持传函数。

这是为了避免把 `ref.current` 在初次渲染时就错误地闭包进来。现在的调用方式是：

```ts
container: () => leftPanelsRef.current
```

这样真正开始拖拽时，拿到的是那一刻最新的 DOM。

第二，比例是按“拖动增量”算的，不是按按下瞬间的鼠标位置直接跳过去。

这是当前实现里一个很重要的交互修正。之前如果在 `pointerdown` 时就立刻按当前位置重算比例，会导致用户只是按下分隔线、还没开始拖，界面就先跳一下。

现在的做法是：

```ts
const pointerStart = axis === "x" ? event.clientX : event.clientY;
const startRatio = layoutRef.current[key];
const delta = currentPointer - pointerStart;
const nextRatio = startRatio + delta / size;
```

也就是说：

- 按下只记录起点
- 真正移动才开始变化

这让拖拽交互更符合直觉。

第三，最小尺寸是在拖拽层被换算成比例的。

实现上会先算出：

```ts
const effectiveSize = Math.max(size, minStart + minEnd);
const minRatio = minStart / effectiveSize;
const maxRatio = 1 - minEnd / effectiveSize;
```

再用 `clamp` 限制结果。

这样写的好处是，不论容器当前尺寸怎么变化，拖拽层看到的始终是统一的比例约束，而不是零散的像素判断。

`Home.tsx` 是怎么把三组分栏接起来的

首页接线并不复杂，但结构一定要清晰。

主分栏对应的是最外层：

```tsx
<div className={style["home-container"]} ref={homeContainerRef}>
  <div
    className={style["width-module"]}
    style={{ flex: `0 0 ${layout.mainSplitRatio * 100}%` }}
  >
    ...
  </div>

  <div
    role="separator"
    aria-orientation="vertical"
    onPointerDown={startResize(...)}
  />

  <div className={style["cofecha-module"]}>
    ...
  </div>
</div>
```

左侧上下分栏接在 `width-panels` 内：

```tsx
<div className={style["width-panels"]} ref={leftPanelsRef}>
  <div
    className={style["data-container"]}
    style={hasProblems ? { flex: `0 0 ${layout.leftBottomRatio * 100}%` } : undefined}
  >
    ...
  </div>

  <div role="separator" ... />

  <div className={style["problems-container"]}>
    ...
  </div>
</div>
```

右侧上下分栏接在 `cofecha-panels` 内：

```tsx
<div className={style["cofecha-panels"]} ref={rightPanelsRef}>
  <div
    className={style["full-text"]}
    style={hasChart ? { flex: `0 0 ${layout.rightBottomRatio * 100}%` } : undefined}
  >
    ...
  </div>

  <div role="separator" ... />

  <div className={style["line-chart"]}>
    ...
  </div>
</div>
```

这里有一个当前实践上的重点：

分隔线本身只是交互入口，真正的布局约束仍然来自 flex 容器和内部内容层，而不是靠分隔线硬控一切。

当前项目里的最小尺寸是怎么分配职责的

这是这套分栏实践里最容易踩坑、也是后来逐步理顺的部分。

一开始很容易本能地想：所有最小宽度、最小高度都写进拖拽逻辑里。

但项目实践下来发现，更合理的做法是分层处理。

主左右分栏：拖拽层不再设置最小宽度

当前主分栏拖拽是：

```ts
startResize({
    key: "mainSplitRatio",
    axis: "x",
    container: () => homeContainerRef.current,
    minStart: 0,
    minEnd: 0,
})
```

也就是说，主分隔线本身不拦截拖拽。

为什么这么做？

因为现在左右两侧都已经有了各自的内容层最小宽度和滚动兜底。如果还在拖拽层硬卡住，会让用户觉得“拖不动”，体验反而更差。

左侧上下分栏：仍保留业务上更合理的最小高度

左侧上下分栏目前仍保留限制：

```ts
minStart: 220,
minEnd: 96,
```

这是因为左侧上半部分是主要工作区，下半部分是问题详情区。如果完全不限制，左下区域会非常容易被压成不可读状态。

右侧上下分栏：拖拽层不再限制，交给滚动条兜底

这是当前和早期方案差异最大的地方之一。

现在右侧上下分栏改成了：

```ts
minStart: 0,
minEnd: 0,
```

也就是：

- 分隔线可以继续往上或往下拖
- 不会在某个固定高度卡住
- 真正装不下时，由 `full-text` 和 `line-chart` 自己出现滚动条

这套策略更适合右侧，因为 COFECHA 文本区和图表区本质上都是“可滚动阅读型面板”，不需要在拖拽层死守一个固定高度。

最小宽度不再挂在外层模块，而是放到内容层

当前最重要的宽度约束并不在拖拽逻辑里，而在 [Home.module.css](</d:/Code/Crossdating_Tauri/src/pages/Home.module.css>)。

左侧主要由这两处定义：

```css
.control-bar {
    min-width: 670px;
}
```

右侧文本和图表的内容宽度由内部包裹层定义：

```css
.cofecha-panel-content {
    min-width: 580px;
}
```

这个做法的意义在于：

- 外层栏目可以继续缩窄
- 真的缩不下时，不是整个页面死掉
- 而是具体面板内部出现滚动条

这比把所有最小宽度都塞进拖拽层更自然，也更符合桌面应用的使用习惯。

CSS 上有哪些关键布局约束

这一部分是分栏能不能稳定工作的基础。

当前首页的核心原则是：

1. 外层负责布局边界。
2. 内层负责滚动。
3. 所有参与 flex 收缩的容器都显式加 `min-height: 0` / `min-width: 0`。

比如：

```css
.home-container,
.width-module,
.cofecha-module,
.width-panels,
.cofecha-panels {
    min-height: 0;
}
```

以及：

```css
.data-container,
.problems-container,
.full-text,
.line-chart {
    min-width: 0;
    min-height: 0;
}
```

如果没有这些约束，子容器很容易因为内容过多把父容器撑开，最后表现成：

- 分栏比例失效
- 某个面板被挤到最底部
- 拖动分隔线时看起来像“没反应”

当前几类容器的职责也已经比较清晰：

- `.home-container` 负责主左右布局
- `.width-panels` / `.cofecha-panels` 负责上下布局
- `.data-container`、`.full-text`、`.line-chart` 负责各自内部滚动

分隔条的样式实践

当前分隔条统一使用 `div + role="separator"`，并通过 `aria-orientation` 标记方向。

样式上统一收敛到：

```css
.panel-divider-vertical {
    width: 2px;
    padding: 0 5px;
    cursor: col-resize;
}

.panel-divider-horizontal {
    height: 2px;
    padding: 5px 0;
    cursor: row-resize;
}
```

其中一个比较实用的处理是：

- 视觉上线只是一条细线
- 实际可点击区域通过 `padding` 扩大

这样更容易拖中，也不会让分隔线看起来太粗。

右侧文本区和图表区后来为什么要改成“各自滚动”

这是本轮实践里一个很值得记的转向。

早期的想法比较直觉：右侧整列可以继续缩，但只要上下分栏达到某个最小高度就停住。

后来用户体验上暴露出两个问题：

1. 用户会感觉“分隔线拖不动了”。
2. 右侧本来就是阅读型区域，完全可以允许更极端的压缩，再交给滚动条处理。

于是当前做法改成：

- 分隔线不限制
- `full-text` 自己 `overflow: auto`
- `line-chart` 自己 `overflow: auto`
- 图表真正的最小可用高度由内部 `.line-chart-content` 承担

这部分样式是：

```css
.line-chart {
    overflow: auto;
}

.line-chart-content {
    min-height: 320px;
}
```

这样做之后，拖拽的手感会明显更一致：

- 分隔线永远能继续拖
- 真正空间不足时，内容自己滚

这套体验比“拖拽突然被硬卡住”更平滑。

右上统计栏的一个小实践

右上统计栏虽然不是分栏本身，但它会明显影响窗口缩放时的体验。

例如 `Mean sensitivity` 如果在缩放过程中被拆成两行，会造成布局抖动，用户会误以为分栏本身不稳定。

所以当前样式里额外做了：

```css
.statics-info span {
    white-space: nowrap;
}
```

这个处理很小，但很符合当前项目的分栏思路：

不是所有问题都该去动拖拽逻辑，有时真正应该稳住的是内容本身的排版行为。

当前这套分栏实践里踩过的几个坑

第一，不能只盯着 splitter 本身。

很多布局问题表面看像是：

- 分隔线没生效
- flex 比例不对
- 某个区域“消失”了

但根因往往是高度链没闭合，或者滚动责任放错了层。

第二，最小尺寸不应该全部写进拖拽层。

主左右分栏和右侧上下分栏现在都把更大的责任交给了内容层滚动。这个转向很关键，因为它让交互从“被拦住”变成“继续拖，只是内容开始滚动”。

第三，交互细节会直接影响用户对布局稳定性的判断。

比如：

- `pointerdown` 时先跳一下
- 统计栏单词自动换行
- `cofecha-selector` 用 `fixed` 脱离面板

这些问题都不是分栏算法本身，但都会让用户觉得“分栏不好用”。

当前实现里已经做了对应修正：

- 拖拽按下不跳
- 统计项不随便断词
- `cofecha-selector` 改为面板内 `sticky`

验证这套分栏是否正常，应该看什么

建议至少手动验证下面这些场景：

1. 左右主分栏能否顺畅拖动，且重启应用后比例仍保留。
2. 左侧上下分栏能否正常拖动，且问题区不会被压到不可读。
3. 右侧上下分栏能否继续拖到很极端的位置，并由各自面板内部滚动兜底。
4. 把窗口缩到很窄时，左侧和右侧是否仍然是“内容滚动”，而不是整页布局崩掉。
5. 右上统计栏在窗口缩放过程中是否还会因为词组断行产生抖动。
6. `cofecha-selector` 是否始终留在文本面板顶部，而不是脱离所属区域。

总结

这套首页分栏的最终结果，不是“多加了三条可拖拽线”这么简单。

它更像是一套逐步收敛出来的界面实践：

1. 用统一 hook 接管拖拽和持久化。
2. 用明确的 flex 结构定义三组分栏。
3. 把最小尺寸从拖拽层逐步转移到内容层。
4. 让不足空间优先转化为内部滚动，而不是硬阻止用户继续拖。
5. 再用一系列小交互修正，把“能用”提升到“手感稳定”。

如果用一句话概括当前这套实现，我会写成：

> 首页分栏的关键不在于“把面板分开”，而在于让拖拽、内容最小尺寸、滚动责任和持久化状态落在各自正确的层级上。
