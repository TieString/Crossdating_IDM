修正虚拟列表在向上滚动时出现“自动下坠”的问题

前言

在这次首页性能优化里，左侧树轮宽度区域从“整表全量渲染”改成了“按序列块虚拟化”。这一步确实明显减轻了窗口缩放和大数据加载时的压力，但也引入了一个新的交互问题：

向下滚动基本正常，向上滚动时，滚动条有时会自己往下掉一点，像是界面偷偷把用户刚刚滚上去的位置又推回去了。

这个问题表面上看像“滚动条失灵”，但本质上并不是单纯的滚动事件问题，而是虚拟列表、浏览器滚动锚定和延迟渲染策略叠加后的结果。

正文

问题现象

本次问题出现在左侧树轮宽度数据区，也就是 `data-container -> WidthContainer -> width-grid-container` 这一条渲染链上。

具体现象有两个特点：

1. 向下滚动时基本正常。
2. 向上滚动时，滚动位置偶尔会被浏览器“纠正”，表现为滚动条自动往下挪一点，像是内容重新加载后把当前位置顶回去了。

这类问题在做虚拟列表时很典型，因为向上滚动意味着“顶部重新补内容”，而顶部内容一旦动态插入，浏览器就会重新考虑当前滚动锚点是否还应该保持在原来的位置。

为什么会发生

这次问题不是由单一原因造成的，而是三个因素叠在一起：

1. 虚拟列表会动态替换顶部和底部的 spacer。
2. 序列块上使用了 `content-visibility: auto`。
3. 浏览器默认开启了 scroll anchoring。

先看第一层。

`WidthContainer` 当前采用的是“块级虚拟化”，也就是：

- 视口外的序列块不真正渲染；
- 用顶部 spacer 和底部 spacer 占位；
- 视口变化时，再把新的序列块补进来。

这种做法本身没有问题，但它意味着 DOM 结构并不是静态的。特别是在向上滚动时，顶部可见块会被重新插入，顶部 spacer 的高度也会变化。浏览器看到顶部内容结构变了，就可能触发滚动位置修正。

再看第二层。

为了继续榨一点性能，之前给 `.series-block` 加了这组样式：

```css
content-visibility: auto;
contain-intrinsic-size: auto 180px;
```

它的作用是：让浏览器对暂时不可见的块延迟绘制，并用一个估算尺寸先占位。

单独使用时，这通常没问题；但放进虚拟列表里就变得微妙了。因为虚拟列表本来就在自己控制“哪些块该出现、哪些块该消失”，此时再让浏览器用 `content-visibility` 继续推迟渲染，相当于两套“可见性管理”叠在一起。

结果就是：

- React 认为块已经补回来了；
- 浏览器却可能还没真正把它完整绘制出来；
- 一旦真实绘制尺寸或锚点判断与预期不一致，滚动位置就会产生轻微回弹。

第三层是 scroll anchoring。

浏览器默认会尽量“帮用户稳定视口”。当容器上方内容发生变化时，它会尝试自动调整 `scrollTop`，避免用户正在看的内容突然跳走。

这在普通长文页面里通常是好事，但放到虚拟列表里，尤其是顶部 spacer 会不断变化的场景里，就可能变成反效果：

- 虚拟列表在补顶部内容；
- 浏览器在试图重新锚定位置；
- 两边都在“帮忙”，最后就会出现向上滚动时被偷偷推回一点的感觉。

还有一个额外的问题是，`width-grid-container` 之前还带着自己的 `overflow: scroll`。虽然主要滚动容器其实是外层 `data-container`，但内部再挂一层滚动上下文，会让滚动责任边界变得不够清晰，也更容易增加调试成本。

修正方案

这次修正没有继续在 `WidthContainer.tsx` 里加更多计算，而是先从 CSS 和滚动策略层面把不稳定因素拿掉。

最终做了三件事。

1. 去掉 `.series-block` 上的 `content-visibility: auto`

```css
@supports (content-visibility: auto) {
    .series-block {
        content-visibility: auto;
        contain-intrinsic-size: auto 180px;
    }
}
```

这一段被整体移除了。

这样做的目的不是否定 `content-visibility`，而是承认一个更重要的原则：

当组件已经在自己做虚拟化时，不要再让浏览器额外接管一层“延迟显示”。

对这个页面来说，块级虚拟化已经是主要性能来源；继续叠加 `content-visibility` 带来的收益有限，但它对滚动稳定性的副作用却是实实在在的。

2. 去掉 `width-grid-container` 自身的 `overflow: scroll`

原先样式里有：

```css
.width-grid-container {
    overflow: scroll;
}
```

这次把它去掉了。

因为真正应该负责纵向滚动的是外层的 `.data-container`。虚拟列表内部最好只负责“撑开内容总高度”和“裁剪渲染范围”，不要再额外创建一层滚动上下文。

这样做之后，滚动责任更单一：

- `data-container` 负责滚动；
- `width-grid-container` 负责内容布局；
- `virtual-spacer` 负责占位。

3. 显式关闭 scroll anchoring

这次分别加到了三个地方：

```css
.data-container {
    overflow-anchor: none;
}

.width-grid-container {
    overflow-anchor: none;
}

.virtual-spacer {
    overflow-anchor: none;
}
```

核心思路很直接：

既然当前这套虚拟列表会主动调整顶部 spacer 和可见块，那就不要再让浏览器帮我们自动修正滚动锚点。

换句话说，我们明确告诉浏览器：

这个滚动容器的位置控制由应用自己负责，不需要你再做“智能纠偏”。

涉及文件

本次修正涉及两个文件：

- `src/components/WidthContainer/WidthContainer.module.css`
- `src/pages/Home.module.css`

改动点非常集中，没有进一步扩散到 `WidthContainer.tsx` 的虚拟化核心逻辑里。

为什么先这样修，而不是立刻重写虚拟化

如果继续往下深挖，下一步当然可以做“真实块高测量”：

- 每个 `series-block` 挂 ref；
- 渲染后回读真实高度；
- 再用真实高度而不是估算高度去更新 spacer。

这会更彻底，但也会把实现复杂度明显抬高。

而这次问题的第一优先级，其实不是“估算误差”，而是“滚动链上有两套甚至三套机制同时在调整位置”：

- 应用自己的虚拟列表；
- `content-visibility` 的延迟渲染；
- 浏览器的 scroll anchoring。

所以更合理的第一步不是立刻重写，而是先把这些互相打架的机制拆开，保留一套最清晰、最可控的滚动模型。

这也是为什么本次修复优先落在 CSS 层，而不是急着把虚拟化逻辑推倒重来。

修正后的结论

这次修正之后，左侧树轮宽度区域的滚动策略应当变成这样：

- 只有 `data-container` 是真正的纵向滚动容器；
- `width-grid-container` 不再自己滚动；
- `virtual-spacer` 只做占位，不参与滚动锚定；
- `series-block` 不再延迟绘制；
- 虚拟列表的可见块切换，不再叠加浏览器的自动滚动修正。

这套组合虽然比“极致性能配置”更保守一些，但在实际交互上更稳，更适合作为当前项目的默认方案。

经验总结

这次问题很适合作为一个前端工程上的提醒：

1. 虚拟列表并不是加得越多优化策略越好。

当组件已经在主动控制渲染窗口时，再叠加 `content-visibility`，不一定是增益，也可能变成两套可见性系统互相打架。

2. 浏览器的“智能行为”并不总是适合工程化场景。

`overflow-anchor` 对普通文档很友好，但对动态 spacer、虚拟列表、无限滚动这些场景，往往需要显式关闭。

3. 滚动容器最好只有一个真正负责人。

如果外层和内层都在处理滚动，哪怕用户看起来“还能滚”，调试和稳定性也会立刻恶化。

4. 修复顺序比修复力度更重要。

遇到这类问题时，优先先拆掉互相干扰的机制，再决定要不要上更复杂的“真实测量”“动态校正”方案，通常是更稳的路径。

后续方向

如果后面仍然出现少量向上滚动抖动，下一步最合理的增强方向是：

- 在 `WidthContainer.tsx` 中记录每个 `series-block` 的真实高度；
- 用真实高度回写虚拟列表的 `top / bottom / totalHeight`；
- 进一步降低估算高度与真实高度不一致带来的滚动误差。

但在当前阶段，先把滚动体验恢复稳定，比继续叠加“理论上的优化项”更重要。
