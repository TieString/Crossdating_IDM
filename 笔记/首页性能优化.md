当首页加载较大的 RWL 数据后，为什么窗口缩放会明显卡顿，我们是怎么一步步把问题复现出来、拆开、验证，再收敛到当前实现的。

为了让这篇笔记可复用，这里不会只写项目结论，也会给出对应的最小示例。也就是说，即使脱离当前项目，只保留 React、一个大列表和一个图表区域，仍然可以复现同类问题。

正文

问题现象

首页性能问题最明显的场景是：

1. 打开一个较大的 RWL 文件。
2. 等左侧树轮宽度区和右侧 COFECHA 区都加载完成。
3. 开始持续拖动窗口边缘，反复改变窗口大小。

此时最直观的体感是：

- 页面会卡顿；
- 左侧大列表重排明显；
- 右下图表也会跟着频繁刷新；
- 如果数据量更大，卡顿会很快从“有点顿”变成“明显掉帧”。

这类问题最容易被误判成“Chart.js 太重”，但项目实践里最后证明，真正的瓶颈并不只在图表，而是三类问题叠在一起：

1. 数据引用不稳定，导致本不该重渲染的组件也重渲染。
2. 左侧宽度表一次性渲染了过多 DOM。
3. 图表在连续 resize 期间仍然参与重绘。

怎么稳定复现

在项目里，直接复现的方法很简单：

1. 打开一个树种数量多、年份跨度大的 `.rwl` 文件。
2. 确保左侧树轮宽度表已经完整显示。
3. 如果右下图表有内容，再持续拖动窗口边缘 3 到 5 秒。
4. 观察界面是否出现明显掉帧。

如果想脱离项目做最小验证，可以先用下面这段模拟数据生成器：

```ts
function createMockSiteData(seriesCount = 120, yearsPerSeries = 400) {
  const site = new Map<string, Map<number, number>>();

  for (let i = 0; i < seriesCount; i++) {
    const code = `TREE_${String(i).padStart(3, "0")}`;
    const yearMap = new Map<number, number>();

    for (let year = 1600; year < 1600 + yearsPerSeries; year++) {
      yearMap.set(year, Math.round(Math.random() * 100));
    }

    site.set(code, yearMap);
  }

  return site;
}
```

只要把这份数据挂到一个“大列表 + 图表”的页面上，再开始 resize，就足够复现大部分问题。

第一类问题：数据引用不稳定

这是最容易被忽视，但在 React 里破坏力很大的问题。

在项目早期，`Home.tsx` 很容易写成这样：

```ts
const siteData = rwlEditorRef.current.getData();
```

表面上看没有问题，但如果 `getData()` 每次都返回一个新的 `Map` 副本，那么：

- 只要 `Home` 重新 render；
- `siteData` 的引用就变了；
- 左侧宽度表和右侧图表会以为“数据更新了”；
- 明明只是窗口尺寸变化，也会触发整条渲染链重新工作。

这类问题的最小示例如下：

```tsx
function BadExample() {
  const sourceRef = useRef(new Map([["a", 1], ["b", 2]]));
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  const data = new Map(sourceRef.current);

  return <HeavyChild data={data} width={width} />;
}
```

这里真正变化的只是 `width`，但 `HeavyChild` 每次都会拿到一份新 `Map`。

更合理的写法是显式维护数据快照：

```tsx
function GoodExample() {
  const sourceRef = useRef(new Map([["a", 1], ["b", 2]]));
  const [dataSnapshot, setDataSnapshot] = useState(() => new Map(sourceRef.current));
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  const mutateData = () => {
    sourceRef.current.set("c", 3);
    setDataSnapshot(new Map(sourceRef.current));
  };

  return <HeavyChild data={dataSnapshot} width={width} onMutate={mutateData} />;
}
```

也就是说：

- 布局变化只更新布局状态；
- 数据变化只更新数据快照；
- 两者不要混在一起。

当前项目里对应的落点在 [Home.tsx](</d:/Code/Crossdating_Tauri/src/pages/Home.tsx>)：

```ts
const [siteDataSnapshot, setSiteDataSnapshot] = useState<RwlSiteData>(() => rwlEditorRef.current.getData());
```

只有在这些真正的数据事件发生时才刷新：

- 打开文件
- 编辑年轮宽度
- 保存
- 另存为后同步基准

这一步的意义不是“更优雅”，而是避免窗口 resize 顺便制造“伪数据更新”。

第二类问题：左侧列表 DOM 太大

这类问题在性能分析里几乎总会出现。

如果左侧树轮宽度表把所有树种、所有年份、所有行一次性挂进 DOM，那么数据一大，浏览器每次 resize 都要重新参与布局计算。

最小错误示例大概像这样：

```tsx
function HugeList({ data }: { data: string[] }) {
  return (
    <div>
      {data.map((item) => (
        <div key={item} className="row">
          {item}
        </div>
      ))}
    </div>
  );
}
```

如果这里不是 100 行，而是几千上万格内容，那么单次 reflow 的代价就会迅速上升。

最小优化方向不是“继续抠 CSS”，而是减少真实渲染量。

一个最小虚拟列表示例可以写成：

```tsx
function VirtualList({ rows, rowHeight, scrollTop, viewportHeight }) {
  const overscan = 200;
  const start = Math.max(0, Math.floor((scrollTop - overscan) / rowHeight));
  const end = Math.min(
    rows.length,
    Math.ceil((scrollTop + viewportHeight + overscan) / rowHeight)
  );

  const topSpacer = start * rowHeight;
  const bottomSpacer = (rows.length - end) * rowHeight;

  return (
    <div>
      <div style={{ height: topSpacer }} />
      {rows.slice(start, end).map((row) => (
        <div key={row.id} style={{ height: rowHeight }}>
          {row.label}
        </div>
      ))}
      <div style={{ height: bottomSpacer }} />
    </div>
  );
}
```

这段示例最重要的思想是：

- 视觉上仍然保留完整滚动高度；
- 实际上只渲染视口附近那一小段内容。

当前项目没有采用“按行绝对定位”的方式，而是最终收敛成了“按序列块虚拟化”。

原因很实际：

- 原始语义是 `series-block -> series-row`
- 一个序列出错，不应该拖垮后面所有序列
- 块内自然文档流更稳，维护成本也更低

当前实现落在 [WidthContainer.tsx](</d:/Code/Crossdating_Tauri/src/components/WidthContainer/WidthContainer.tsx>)，核心结构是：

```ts
interface VirtualSeries {
  treeCode: string;
  rows: VirtualRow[];
  top: number;
  height: number;
  bottom: number;
}
```

再通过：

- `findVisibleStartIndex`
- `findVisibleEndIndex`
- `topSpacerHeight`
- `bottomSpacerHeight`

只渲染当前视口附近的 `visibleSeries`。

对应 JSX 的核心结构其实很简单：

```tsx
<div className="width-grid-container">
  <div style={{ height: topSpacerHeight }} />
  {visibleSeries.map((series) => (
    <div className="series-block" key={series.treeCode}>
      {series.rows.map((row) => (
        <div className="series-row" key={row.startYear}>
          ...
        </div>
      ))}
    </div>
  ))}
  <div style={{ height: bottomSpacerHeight }} />
</div>
```

也就是说，这次真正有决定性效果的不是某一条 CSS，而是：

> 把“整张表一起渲染”变成了“只渲染当前可视区附近的序列块”。

第三类问题：图表在 resize 期间过于积极

如果右下 Chart.js 图表在用户连续拖动窗口边缘时，每一帧都立即跟着重绘，那么掉帧几乎是必然的。

这个问题的最小错误示例如下：

```tsx
function BadChartArea() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  return <HeavyChart width={width} />;
}
```

这里用户每拖一次窗口，图表就重绘一次。

更稳妥的最小改法不是一上来就“彻底禁用 resize”，而是区分：

- 用户正在持续 resize
- 用户已经停下来了

最小示例：

```tsx
function BetterChartArea() {
  const [isResizing, setIsResizing] = useState(false);
  const timerRef = useRef<number | null>(null);

  useEffect(() => {
    const handleResize = () => {
      setIsResizing(true);

      if (timerRef.current !== null) {
        window.clearTimeout(timerRef.current);
      }

      timerRef.current = window.setTimeout(() => {
        setIsResizing(false);
        timerRef.current = null;
      }, 160);
    };

    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);

  return isResizing ? <div>正在调整窗口...</div> : <HeavyChart />;
}
```

这并不是“偷懒不渲染”，而是明确告诉 UI：

连续 resize 是一个高频中间态，不值得把最重的图表也拖进来一起刷新。

当前项目在 [Home.tsx](</d:/Code/Crossdating_Tauri/src/pages/Home.tsx>) 里就是这么做的：

- 用 `isWindowResizing` 标记是否正在连续 resize
- 用 `160ms` 的定时器识别 resize 结束
- 结束前显示轻量占位提示
- 结束后再恢复真实 `TreeChartManager`

配套上，图表自身也补了两个基础前提：

- [TreeChartManager.tsx](</d:/Code/Crossdating_Tauri/src/components/Chart/TreeChartManager.tsx>) 用 `memo` 包裹
- [MultiLineChart.tsx](</d:/Code/Crossdating_Tauri/src/components/Chart/MultiLineChart.tsx>) 开启 `maintainAspectRatio: false`

这样图表至少会：

- 真正吃满剩余高度
- 不至于在容器变化时反复走一套不必要的尺寸推导

为什么没有继续迷信 `contain` 和 `content-visibility`

这次优化过程中也尝试过更轻量的方式，比如：

- `contain: layout`
- `content-visibility`
- 只调图表参数

这些不是没用，但它们解决的是“浏览器怎么更省一点”，而不是“我们到底还应不应该渲染这么多东西”。

换句话说：

- 如果 DOM 规模本身没变，轻量优化只是止痛药；
- 真正决定体感的，仍然是数据引用稳定和真实渲染量下降。

而且项目后来还发现，虚拟列表和 `content-visibility` 叠加，会引出向上滚动回弹的问题。这也进一步说明：

性能优化不是堆越多特性越好，而是要先确定哪一层才是真瓶颈。

怎么验证优化确实有效

这部分尽量用可操作的步骤来记录。

项目内验证方法

1. 打开一个较大的 `.rwl` 文件。
2. 观察左侧宽度表是否只在滚动视口附近渲染内容。
3. 持续拖动窗口边缘 3 到 5 秒。
4. 对比优化前后的体感差异：
   - 左侧列表是否仍然明显掉帧
   - 右下图表是否在连续 resize 期间先进入占位状态
   - 停止 resize 后图表是否恢复

最小示例验证方法

可以准备三组组件做 A/B 对照：

1. `BadExample`
   每次 render 都生成新数据引用。

2. `HugeList`
   一次性渲染所有行。

3. `BadChartArea`
   resize 时实时重绘图表。

然后依次替换成：

1. `GoodExample`
2. `VirtualList`
3. `BetterChartArea`

只要数据量足够大，这三组对照在实际拖动窗口时会有非常明显的差异。

当前项目里最终保留下来的关键实践

如果只保留最有价值的结论，我会把这次首页性能优化总结成三条：

1. 数据快照化

在 [Home.tsx](</d:/Code/Crossdating_Tauri/src/pages/Home.tsx>) 里，把 `siteData` 从“每次 render 重新生成”改成“真正改数据时才更新的快照状态”。

2. 左侧大表块级虚拟化

在 [WidthContainer.tsx](</d:/Code/Crossdating_Tauri/src/components/WidthContainer/WidthContainer.tsx>) 里，按 `series-block` 做可视区渲染，用 spacer 维持总高度。

3. 连续 resize 期间让图表降载

在 [Home.tsx](</d:/Code/Crossdating_Tauri/src/pages/Home.tsx>) 里，识别 resize 中间态，暂时不渲染真实图表。

这三件事里，真正最关键的是前两件，因为它们改变的是渲染规模和渲染触发条件，而不是只在浏览器层做局部补救。

经验总结

这次首页性能优化最值得记住的不是某个技巧，而是一个判断顺序：

1. 先确认是不是“数据引用变化”把无关组件拖下水了。
2. 再确认是不是“真实渲染量过大”。
3. 最后才去做 `contain`、`content-visibility`、图表参数这类局部调优。

如果顺序反过来，就很容易陷入：

- 改了很多细节
- 页面还是卡
- 但又很难说清楚为什么

而一旦能把问题压缩成最小示例，性能问题就会从“感觉不太行”变成“这里每次 resize 都在做不该做的工作”。

总结

这次首页性能优化，本质上不是“页面更快了”这么抽象，而是把一个真实的卡顿问题拆成了三个可复现的小问题：

1. 不稳定的数据引用
2. 过大的列表渲染量
3. 连续 resize 时过于积极的图表刷新

当这三个问题都被分别证明、分别修掉之后，项目里的优化路径也就自然清晰了。

如果用一句话概括这篇笔记，我会写成：

> 性能优化最有效的起点，不是先找技巧，而是先把“为什么卡”缩成一个你能独立复现的最小例子。
